## 前言 Introduction

### 背景 Background

自从当了家庭煮夫，发现买菜真的是一件费心费力的大难题。常常会出现买了菜回来不久，发现有个备货没了应该再去一趟。在国内的话还好说，澳洲是真的需要自己去跑超市。所以准备做个APP，把家里有什么东西、什么东西需要补货都管理起来。

目前这个软件已经上线了，还是非常早期的版本（`v0.0.1`），但是已经可以满足基本需求了，后续也会不断地迭代优化。所以今天就来介绍一下如何部署到Azure上。

考虑到这是我做的第一个全栈开发的APP，有关这个APP的其它技术细节后续也会写一系列博客更新。

### 需求 Requirements

我的APP主要包含三个部分的内容：数据库（Database），后端（Backend），前端（Frontend）。这三个部分都需要部署到Azure上，同时考虑到是个比较小的个人项目，价格希望也尽可能低廉，能白嫖就要白嫖。

另外，考虑到APP后面维护更新的流程，也需要实现自动化部署的脚本。这样我进行代码修改和本地调试之后，可以一键部署，不需要再手动操作。

## 部署方案

我最终确定的解决方案如下。

### Database: PostgreSQL Flexible Server

由于数据库框架为`PostgreSQL`，我决定使用`Azure Database for PostgreSQL Flexible Server`。

这个服务对新账户来说前12个月免费，免费额度为每个月750小时的计算资源和32Gb的存储空间。超过了之后，每个月基础费用估算约为23.4美元。

后续我如果觉得这个价格略高，可能也会考虑更换其它Database服务或是干脆直接使用我自己的VPS进行搭建，但现阶段准备先使用这个。

### Backend：Function App

具体来说，使用的是 `Azure Functions App`。我的后端架构为Python FastAPI，这个框架可以直接被转化为适用于 Function App 的形式。

另外一个给后端的选择是 `Azure App Service`，但考虑我应用的实际情况，最终还是选择了Function App。这两个的主要区别为：

- `Azure Functions App`本质上托管的是Function，只有在调用的时候才占用资源，按照调用次数收费。
- 而`App Service`则是全时段在线，收费基准为运行时间。

免费情况下，App Service只有每天60分钟的CPU时间，而Function则是每天100000次调用。在少量朋友一起对APP进行测试的环境下，60分钟时间是不太够用的。

不过相较于全天候在线的 App Service，Function App 在调用的时候会涉及到冷启动问题。个人实测，使用 Function App 时，调用API会有3-4秒的延迟。但是考虑到可以通过优化前端逻辑、使用草稿功能来减少调用API的次数，这个延迟应该是可以接受的。

### Frontend：Static Web App

`Azure Static Web Apps`的服务可以托管静态网站，免费额度非常多，基本不用另外花钱。

我的前端平台为React Expo，build出来的静态网站可以托管在这个服务上。

另外，部署完前端之后会需要购买一个新的域名。准备从Namesilo购买（因为最便宜），同时使用我一直用得比较习惯的 CloudFlare 进行DNS的托管。

### Deployment：Github Workflows

由于我的代码都是托管在Github上面的，因此使用workflow进行部署是最为自然的。
